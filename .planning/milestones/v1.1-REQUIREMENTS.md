# Requirements: Nova

**Defined:** 2026-07-11
**Core Value:** A private, fully local household assistant that Ruben & Méral can reach by text or voice, keeping a shared plan (tasks, calendar, important email) — reasoning and data never leave the house.

## v1 Requirements

Requirements for this milestone (roadmap Phase 4-8 plus Track A1/A2, pulled forward per research). Each maps to roadmap phases.

### WhatsApp Channel

- [x] **WA-01**: User can message Nova via WhatsApp and receive a reply attributed to them by phone number
- [x] **WA-02**: Nova verifies WhatsApp webhook signatures against the raw, unparsed request body before processing (framework auto-JSON-parsing must not break the HMAC check)
- [x] **WA-03**: Messages from unrecognized WhatsApp senders are handled gracefully (fallback to household identity, not a crash or silent drop)

### Household Tasks

- [x] **TASK-01**: User can create a task via natural-language request with the correct default assignee (message sender, unless a different person is explicitly named)
- [x] **TASK-02**: User can set a task deadline via natural language, including relative dates ("Thursday 4pm", "tomorrow morning"), resolved against an explicit current-date/time anchor rather than raw LLM date math
- [x] **TASK-03**: User can list open tasks, filterable by assignee or due date
- [x] **TASK-04**: User can mark a task complete
- [x] **TASK-05**: Malformed or mismatched LLM tool-call arguments are validated and reported, not silently dropped (fixes the existing `Tool.run` gap before real backends go live)

### Calendar

- [x] **CAL-01**: User can create a calendar event via natural-language request, including relative date/time
- [x] **CAL-02**: User can query the calendar via natural language ("what's on tomorrow?", "when's the dentist?")
- [x] **CAL-02**: Calendar reads/writes handle timezones and recurring events (RRULE) correctly, not just single non-recurring events

### Email

- [x] **EMAIL-01**: Nova flags incoming shared-mailbox email as "important" using a conservative hybrid approach (known senders/keywords first, LLM judgment only on the ambiguous remainder)
- [x] **EMAIL-02**: User can query which emails were flagged important, via chat or voice
- [x] **EMAIL-03**: MS Graph app permissions are scoped to only the shared household mailbox (via Application Access Policy / RBAC for Applications), not tenant-wide

### Voice Channel

- [x] **VOICE-01**: User can ask Nova a question via a voice satellite (ESPHome + Wyoming Whisper/Piper through HA Assist) and receive a spoken answer
- [x] **VOICE-02**: User can ask Nova a question via iPhone (HA Companion Assist) and receive a spoken answer
- [x] **VOICE-03**: Voice round-trip latency stays acceptable when the chat model and Whisper STT run concurrently on the shared GPU (validated under concurrent load, not just idle coexistence)

### Proactive Behavior

- [x] **PROACTIVE-01**: Nova sends each user a morning briefing (tasks due, today's calendar, flagged-important email)
- [x] **PROACTIVE-02**: Nova sends reminders for upcoming or overdue tasks
- [x] **PROACTIVE-03**: Nova pushes a notification when a new "important" email arrives
- [x] **PROACTIVE-04**: Proactive WhatsApp pushes sent outside the 24-hour customer-service window use a pre-approved message template, not free text

### Dashboard

- [x] **DASH-01**: A LAN-only static dashboard shows the same calendar/task data available via chat and voice
- [x] **DASH-02**: Dashboard auto-refreshes on a polling interval with zero user interaction required
- [x] **DASH-03**: Dashboard groups tasks by assignee and flags overdue items

### Write Confirmation

- [x] **CONFIRM-01**: Destructive or externally-visible write actions (delete event, send email) require a lightweight, channel-appropriate confirmation step before executing (voice confirms verbally, WhatsApp uses a quick-reply/text confirm) — minimal version only; full activity feed/audit trail is v2 (see TRUST-01)

### Test Harness (Track A1)

- [x] **TEST-01**: A pytest suite covers nova-core (identity mapping, tool registry, agent loop with a mocked LLM, WhatsApp webhook signature verification) and ops-bridge (dedup/fingerprint)
- [x] **TEST-02**: A failing test suite blocks the Docker image build (`RUN pytest` build-stage step) and therefore the Coolify deploy — not just a post-deploy healthcheck
- [x] **TEST-03**: `heal.sh` runs the test suite before committing an automated fix, rejecting a heal branch with failing tests

### Agent Eval Suite (Track A2)

- [x] **EVAL-01**: A golden-conversation eval suite runs tool-calling scenarios against the real local model: task creation, date parsing (incl. Dutch/English input), multi-tool turns, and refusal cases
- [x] **EVAL-02**: Evals run automatically on changes to the system prompt, tool specs, or `NOVA_MODEL`, with a realistic (non-100%) pass threshold so the gate doesn't become noise

## v1.1 Requirements

> **Status: ACTIVE.** These requirements are roadmapped for Milestone 1.1 (Phases 7-10) and are currently being executed.

Requirements for the "User Preferences" milestone: self-service WhatsApp onboarding, per-user scheduled job toggles/times (incl. new weekly briefing), and per-user DND windows. Informed by `.planning/research/SUMMARY.md`.

### WhatsApp Onboarding & Identity

- [ ] **ONBOARD-01**: User can start a WhatsApp-linking flow from the dashboard by selecting their household identity (Ruben/Méral)
- [ ] **ONBOARD-02**: User enters a WhatsApp number and Nova sends a one-time verification code to that number via a Meta-approved AUTHENTICATION template
- [ ] **ONBOARD-03**: User confirms the code on the dashboard before the number is linked to their account; codes are single-use, expire, and are rate-limited against guessing
- [ ] **ONBOARD-04**: A WhatsApp number can be linked to only one user at a time; claiming an already-linked number is rejected
- [ ] **ONBOARD-05**: User can re-link/replace their linked WhatsApp number if it changes
- [ ] **ONBOARD-06**: Ruben & Méral's existing statically-configured numbers are seed-migrated into the new DB-backed preferences store atomically with the schema change, so WhatsApp access is never interrupted during cutover
- [ ] **ONBOARD-07**: Nova's WhatsApp identity resolution reads exclusively from the DB-backed store after migration — no remaining code path reads the old `NOVA_WHATSAPP_USERS` env var

### Scheduled Job Preferences

- [ ] **PREF-01**: User can toggle their morning briefing on/off
- [ ] **PREF-02**: User can choose the time of day their morning briefing is sent
- [ ] **PREF-03**: A new weekly briefing job summarizes the upcoming week's tasks and calendar
- [ ] **PREF-04**: User can toggle their weekly briefing on/off
- [ ] **PREF-05**: User can choose the day of week and time of day their weekly briefing is sent
- [ ] **PREF-06**: Scheduled jobs fire according to the household's actual local timezone, not UTC (fixes a pre-existing bug uncovered during research)
- [ ] **PREF-07**: Preference changes (toggle or time edits) take effect immediately without a service restart

### Do Not Disturb

- [ ] **DND-01**: User can configure a DND window (start time, end time) that correctly handles a window crossing midnight
- [ ] **DND-02**: Proactive pushes (briefings, task reminders, important-email alerts) are suppressed during the recipient's own DND window
- [ ] **DND-03**: Alerts suppressed by DND (overdue-task reminders, new-important-email notifications) are deferred and delivered once the DND window ends, rather than silently dropped
- [ ] **DND-04**: DND never affects inbound chat — a user messaging Nova during their own DND window still receives an immediate reply

## v2.0 Requirements

Requirements for the **"Reliability & Security Hardening"** milestone (the *current* milestone). Scoped to the still-open, code-solvable concerns from `.planning/codebase/CONCERNS.md` — Reliability + Security buckets only. Each maps to roadmap phases (numbering continues from v1.1 → starts at Phase 11).

### Reliability

- [x] **RELI-01**: Transient Ollama failures are retried with bounded backoff before the turn fails, rather than failing outright on the first error (`services/nova-core/app/llm.py`)
- [x] **RELI-02**: An unhandled LLM or tool error returns a friendly fallback reply to the user (e.g. "Nova is having trouble right now"), never a raw HTTP 500 with a stack trace (`services/nova-core/app/main.py`, `agent.py`)
- [x] **RELI-03**: A single chat turn is bounded by an overall wall-clock budget across the entire tool-calling loop, not just the 6-iteration count (`services/nova-core/app/agent.py`)
- [x] **RELI-04**: Conversation history is truncated to a bounded window before being sent to the model, so a long-running channel conversation cannot grow the request payload past the context window (`services/nova-core/app/agent.py`)

### Security

- [x] **SEC-01**: The chat API (`POST /v1/chat/completions`) authenticates the caller (e.g. shared-secret/per-channel header) before trusting the `user` attribution field, closing trivial household-member spoofing (`services/nova-core/app/main.py`)
- [x] **SEC-02**: ops-bridge compares its `X-Bridge-Token` in constant time via `hmac.compare_digest`, not Python `!=` (`services/ops-bridge/app.py`)

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

|| Feature | Reason |
||---------|--------|
|| Cloud LLM fallback (e.g. "use GPT-4 when the local model struggles") | Violates the non-negotiable privacy boundary — reasoning never leaves the box; fall back to a smaller/faster local model instead |
|| Full inbox summarization / read-everything digest | Alert fatigue at real mailbox volume; defeats the point of triage |
|| Real-time push/websocket architecture for the dashboard | Unnecessary complexity — simple polling refresh is indistinguishable in practice for a household-of-two wall display |
|| Fully autonomous write actions with zero confirmation | Trust-destroying failure mode; every write tool ships with at least minimal confirmation (CONFIRM-01) |
|| Native mobile app | WhatsApp + voice + LAN dashboard already cover every channel this household needs |
|| Broad "AI decides everything" email classification with no deterministic guardrails | Asymmetric cost of false negatives (missed school deadline) vs. false positives (alert fatigue); hybrid rules+LLM approach required instead (EMAIL-01) |
|| Chatty/verbose assistant personality | Friction, not charm, for a utility used dozens of times a day over WhatsApp/voice; terse responses enforced via system prompt, not a feature |
