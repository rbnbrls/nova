<objective>
Build the image processing pipeline for WhatsApp photo intake: detect image messages, download
photo bytes from Meta servers, and analyze them via a local Ollama vision model to extract
structured content (dates, events, tasks, summary).

Purpose: This is the data-ingestion half of the Phase 37 flow — every WhatsApp photo must be
fetched and interpreted before the agent can propose actions. Keeping it entirely on GPU means
no cloud vision API is ever contacted.

Output:
- `app/vision.py` with `analyze_image(image_bytes)` that returns structured extraction dict
- `download_whatsapp_media(media_id)` in WhatsApp adapter
- Image-message branching in the inbound handler
- Config key `nova_vision_model` for Ollama vision model selection
</objective>

    **1. Add `download_whatsapp_media(media_id: str) -> bytes | None`**

    Append this async function (per D-06, D-07):
    - Accept `media_id` string from the WhatsApp payload (e.g. messages[0].image.id)
    - Steps:
      a. Return None immediately (with mock log) if `settings.whatsapp_access_token` is empty/unconfigured
      b. Call Meta Graph API: `GET https://graph.facebook.com/v18.0/{media_id}` with header
         `Authorization: Bearer {settings.whatsapp_access_token}`
      c. From the response JSON extract `url` — the temporary download URL
      d. `GET` that download URL with the same auth header
      e. Return raw response content (bytes)
      f. On any httpx error (timeout, HTTPStatus 4xx/5xx), log and return None
    - Use `try/except` around each HTTP call; log failures with `print(f"[ERROR] ...")` per existing patterns
    - Do NOT import or reference any cloud vision SDK — all fetching done via httpx (per D-03)

    **2. Modify `WhatsAppAdapter.process_incoming()` and `process_incoming_whatsapp()`**

    `WhatsAppAdapter.process_incoming()` currently reads `msg.get("text", {}).get("body", "")`.
    Also attempt to extract image media ID from the payload path `msg.get("image", {}).get("id")`.
    Store the media ID in the `InboundMessage` — however `InboundMessage` currently only has
    `text`. Per D-05 ("reuse existing handler"), add an optional `media_id: str | None = None`
    field to the `InboundMessage` dataclass (in `app/channels/__init__.py`). If image ID is
    present, set `media_id` and leave `text` as an empty string.

    The module-level `process_incoming_whatsapp(payload)` function:

    After resolving the user / sending refusal for unrecognized users, detect whether the
    message has a media_id (image message). If `inbound.media_id` is present:
      a. Call `download_whatsapp_media(inbound.media_id)` to get bytes
      b. If bytes returned, call `await analyze_image(image_bytes)` (imported from
         `app.vision` — created in Task 2)
      c. Build a system-context message from the extraction result and pass it to
         `run_agent` alongside the user message — the vision analysis is piped into the
         agent as context so the LLM can reason about the extracted content.
      d. If bytes are None (download failed), send the user a message:
         "I could not download the photo you sent. Please try again or send the text directly."
      e. If `analyze_image` fails, send: "I had trouble reading that photo. Could you type the important details instead?"

    For step (c), the approach: instead of passing the raw user message text (which is
    empty for image-only messages), create a synthetic message:
    ```
    "[User sent a photo. Vision analysis: {extraction.summary}
     Extracted events: {extraction.events}  Extracted tasks: {extraction.tasks}]"
    ```
    This gives the LLM the context it needs to call `process_photo` (created in a later plan).

    Create `/services/nova-core/app/vision.py` with:

    **1. `analyze_image(image_bytes: bytes, model: str | None = None) -> dict`**

    This is the single entry point for vision analysis. Per D-01, D-02, D-03:

    - Accept raw image bytes (JPEG/PNG per D-07 — these are the formats WhatsApp sends)
    - Accept optional `model` parameter; default reads `settings.nova_vision_model`
    - Build a prompt that asks the vision model to extract structured information from
      the photo — the prompt must use "what information" framing (not "OCR the text") per
      D-02 (vision model handles both text and scene understanding, no separate OCR pipeline).
    - The prompt structure:
      ```
      "You are analyzing a photo of a document or letter sent to a household assistant.
       Extract the following if present:
       - A one-paragraph summary of what this document/photo contains
       - Any calendar events mentioned (title, start date/time, end date/time, description)
       - Any tasks or action items (title, who it's for, due date)
       Respond in JSON format with keys: summary, events, tasks.
       events is an array of objects with keys: title, start, end, description
       tasks is an array of objects with keys: title, assignee, due_at
       Use ISO 8601 format for dates and datetimes.
       If no events or tasks are found, return empty arrays."
      ```
    - Encode image bytes as base64 for the Ollama API `images` field
    - Call Ollama using an async httpx POST to `{settings.ollama_base_url}/api/chat`
      (same endpoint as `app/llm.py` but with `images` in the message payload)
    - Payload format:
      ```python
      {
          "model": model or settings.nova_vision_model,
          "messages": [{
              "role": "user",
              "content": prompt,
              "images": [base64_string]
          }],
          "stream": False,
          "format": "json"  # if available in this Ollama version; omit if causing errors
      }
      ```
    - Parse response JSON from `response.json()["message"]["content"]`
    - Try `json.loads()` on the response content — vision models may wrap JSON in
      markdown code fences; if so, strip backticks and try again
    - On ValueError for JSON parse, log the raw response and return error dict
    - On httpx errors, log and return error dict
    - Return dict structure:
      ```python
      {
          "summary": str,
          "events": list[dict],
          "tasks": list[dict],
          "error": str | None  # only present on failure
      }
      ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WhatsApp → Nova API | Untrusted inbound webhook with user-provided photo content |
| Nova → Meta Graph API | Outbound fetch of media from Meta servers (trusted transport, user-originated content) |
| Nova → Ollama | Local GPU process — no network boundary, but image data from untrusted source enters local model |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37-01 | Spoofing | POST /webhooks/whatsapp | high | mitigate | Existing HMAC-SHA256 signature verification guards against forged payloads including image messages |
| T-37-02 | Tampering | vision.py / analyze_image | low | accept | Maliciously crafted images could cause model hallucination; the confirmation gate (Plan 2) lets users reject incorrect extractions |
| T-37-03 | Information Disclosure | vision.py | medium | mitigate | All processing stays on local Ollama — no image data leaves the GPU (per D-03). Ensure no file cache persists image bytes beyond the request lifecycle |
| T-37-04 | Denial of Service | download_whatsapp_media | low | mitigate | Meta API fetch has a 20s httpx timeout; failure returns None and user gets a friendly error message |
| T-37-05 | Tampering | download_whatsapp_media | low | accept | Meta API download URL is short-lived and generated by Meta; MitM on the download would require prior TLS compromise |
| T-37-SC | Supply Chain | Ollama vision model install | high | mitigate | Human must run `ollama pull llava` — verify model source at ollama.com/library/llava; slopcheck before install |
</threat_model>
