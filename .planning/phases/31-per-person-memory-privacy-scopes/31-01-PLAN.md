    Add to `app/db.py`:
    ```python
    async def get_user_memories(user_name: str) -> str:
        """Return formatted memories for a user: their private + all household-scope memories."""
        pool = await get_pool()
        async with pool.acquire() as conn:
            user_id = await conn.fetchval("SELECT id FROM users WHERE name = $1", user_name)
            if not user_id:
                return ""
            rows = await conn.fetch(
                """
                SELECT content, scope FROM memories
                WHERE (user_id = $1 AND scope = 'private') OR scope = 'household'
                ORDER BY created_at DESC LIMIT 20
                """,
                user_id
            )
        if not rows:
            return ""
        lines = [f"- {r['content']} [{r['scope']}]" for r in rows]
        return "\n".join(lines)
    ```

    Then import in `agent.py`:
    ```python

    ```
    And in `scheduler.py`:
    ```python

    ```

    In `agent.py`, add the `from .db import get_pool, get_user_memories` import (keeping existing get_pool import).
    Remove the local `_get_user_memories` from agent.py if written there — use `get_user_memories` from db.py.

    **Key privacy invariant (D-04):** The SQL query `(user_id = $1 AND scope = 'private') OR scope = 'household'` is THE enforcement point. It ensures:

    - A user NEVER gets another user's private memories (because `(user_id = $1 AND scope = 'private')` only matches rows where user_id equals the querying user, and 'household' rows have no user_id filter restriction — they're returned for everyone)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent-loop → memories DB | Agent retrieves memories scoped to the requesting user — private memories of other users must never cross this boundary |
| LLM → tool call | LLM-generated arguments for `remember`/`forget`/`list_memories` are untrusted input |
| dashboard-browser → memories DB | Planned in 31-02, but the backend API must enforce same scope rules |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-31-01 | Information Disclosure | `get_user_memories()` SQL in `db.py` | critical | mitigate | SQL WHERE clause `(user_id = $1 AND scope = 'private') OR scope = 'household'` enforces per-user scope — no code path returns another user's private memories. Parameterized queries prevent injection. |
| T-31-02 | Tampering | `forget` tool in `memory.py` | high | mitigate | DELETE WHERE includes `user_id = $1` (resolved from authenticated `user` param) — users cannot delete memories they don't own. Scope parameter is optional, not an override. |
| T-31-03 | Spoofing | `user` parameter propagation | high | mitigate | The `user` value is resolved by the agent loop from authentication (API token / voice room / WhatsApp identity) — tools do not accept `user` from LLM-generated args. `Tool.run()` injects `user` from `run_agent(user=resolved_user)` as a separate parameter not in the JSON Schema. |
| T-31-04 | Elevation of Privilege | `scope` parameter in `remember` | medium | mitigate | The tool's JSON Schema enum `["private", "household"]` prevents LLM from passing arbitrary scope values. A malicious LLM output would still be caught by `jsonschema.validate` before execution. |
| T-31-SC | Tampering | pip installs | high | mitigate | No new pip dependencies introduced by this plan; uses only existing imports already in requirements.txt. |
</threat_model>
