<action>

Replace the stub in `services/nova-core/app/maintenance/backup_verifier.py` with a real async implementation of `run_backup_verification()`.

**Flow:**

```
run_backup_verification()
  │
  ├── 1. Check maintenance_backup_verify_enabled (config toggle)
  ├── 2. Find latest dump file:
  │      - List files in settings.backup_dump_dir matching settings.backup_dump_pattern
  │      - Sort by mtime descending, take the most recent
  │      - If no dump files found → log warning, file Forgejo issue:
  │        "[maintenance] backup verification: no dump files found ({date})"
  │        label: "maintenance,backup"
  │        → return
  ├── 3. Create scratch Postgres container via docker subprocess:
  │      - docker run -d --name nova-backup-verify-{timestamp}
  │        -e POSTGRES_PASSWORD=verify
  │        postgres:16-alpine
  │      - Wait for container healthy (poll pg_isready, max 30s)
  ├── 4. Restore dump into scratch container:
  │      - cat {dump_file} | docker exec -i nova-backup-verify-{timestamp}
  │        psql -U postgres
  │      - If restore fails → file issue, clean up container, return
  ├── 5. Run verification SELECT query:
  │      - docker exec -i nova-backup-verify-{timestamp}
  │        psql -U postgres -t -c "SELECT count(*) FROM information_schema.tables WHERE table_schema = 'public';"
  │      - docker exec -i nova-backup-verify-{timestamp}
  │        psql -U postgres -t -c "SELECT count(*) FROM information_schema.columns;"
  │      - Parse integer results from stdout
  │      - docker exec -i nova-backup-verify-{timestamp}
  │        psql -U postgres -t -c "SELECT schemaname || '.' || tablename, n_live_tup FROM pg_stat_user_tables ORDER BY n_live_tup DESC;"
  │      - Parse table row counts
  ├── 6. Determine success:
  │      - Tables count > 0 → SUCCESS
  │      - Tables count == 0 → FAILURE (dump restored but empty)
  │      - Query error → FAILURE
  ├── 7. Cleanup:
  │      - docker stop nova-backup-verify-{timestamp} (with 10s timeout)
  │      - docker rm -f nova-backup-verify-{timestamp}
  ├── 8. File Forgejo issue (or update existing open issue for today):
  │      - SUCCESS: check if an open issue with label "maintenance,backup" exists
  │        for today's date. If yes, comment with verification results.
  │        If no, create issue:
  │        "[maintenance] backup verification OK ({date})"
  │        Body: dump file name, size, table count, row counts per table, restore time
  │        Label: "maintenance,backup"
  │      - FAILURE: create or comment on open issue
  │        "[maintenance] backup verification FAILED ({date})"
  │        Body: dump file attempted, error details, container logs snippet
  │        Label: "maintenance,backup,heal-failed"
  └── 9. Log outcome
```

Implementation notes:

- All docker commands use `asyncio.create_subprocess_exec` with 120-second timeout per call.
- Docker container name: `nova-backup-verify-{YYYYMMDD-HHMMSS}` — uses timestamp to avoid collision.
- Use Postgres 16 alpine image (matching production: `pgvector/pgvector:pg16`). The pgvector image is preferred for compatibility, fallback to `postgres:16-alpine` if the former is too large.
- The restore target database name is `postgres` (the default DB in the scratch container).
- Verify container health: loop `docker exec {name} pg_isready -U postgres` up to 30 times with 1s delay.
- If docker socket is not available (e.g., running in test environment), log a warning and return gracefully.
- Guard: if `settings.backup_dump_dir` directory does not exist, log warning and file issue about missing backup directory.

Edge cases:
- Dump file is 0 bytes → treat as no dump found
- Docker container create fails (port conflict, already exists) → clean up any stale container first with `docker rm -f {name} || true`
- Restore takes longer than 120s → time out, report failure

The module exports `run_backup_verification()` as the scheduler entry point, matching the stub signature from Plan 1.

<action>

Replace the stub in `services/nova-core/app/maintenance/trend_reporter.py` with a real async implementation of `run_trend_report()`.

**Flow:**

```
run_trend_report()
  │
  ├── 1. Check maintenance_trend_report_enabled (config toggle)
  ├── 2. Collect system metrics:
  │      ┌───────────────┬──────────────────────────────────────┐
  │      │ Metric        │ Source                                │
  │      ├───────────────┼──────────────────────────────────────┤
  │      │ Disk usage %  │ shutil.disk_usage('/')               │
  │      │ Disk used GB  │ shutil.disk_usage('/').used / 1e9    │
  │      │ Disk total GB │ shutil.disk_usage('/').total / 1e9   │
  │      │ Docker overlay│ shutil.disk_usage('/var/lib/docker') │
  │      │               │ (if accessible inside container)     │
  │      │ VRAM total MB │ nvidia-smi --query-gpu=memory.total  │
  │      │ VRAM used MB  │ nvidia-smi --query-gpu=memory.used   │
  │      │ GPU temp C    │ nvidia-smi --query-gpu=temperature.gpu│
  │      │ GPU util %    │ nvidia-smi --query-gpu=utilization.gpu│
  │      │ Postgres size │ SELECT pg_database_size('nova')      │
  │      └───────────────┴──────────────────────────────────────┘
  ├── 3. Load previous readings:
  │      - Check for an open "maintenance,trend" issue
  │      - If exists, fetch its body via ForgejoClient.body()
  │      - Parse the previous readings from the issue body
  │      - If no previous issue exists, this is the first run
  ├── 4. Build trend comparison:
  │      - For each metric, compute: current_value, previous_value, delta, delta_pct
  │      - Highlight metrics that changed >10% week-over-week
  │      - Highlight disk usage >80%, VRAM >90%, GPU temp >80C
  ├── 5. File Forgejo issue:
  │      - If no open issue for "maintenance,trend" exists:
  │        Create new issue:
  │        "[maintenance] system trend report ({date})"
  │        Body includes:
  │          * Summary banner: OK / WARNING / CRITICAL based on alert thresholds
  │          * Table: Metric | Current | Previous | Delta | Δ%
  │          * Alerts section: any thresholds exceeded
  │          * Postgres DB size trend
  │        Label: "maintenance,trend"
  │      - If an open issue already exists:
  │        Append this week's data as a comment on the existing issue
  │        (treat it as running log; close + reopen when it gets too long)
  └── 6. Log outcome
```

Implementation notes:

- `shutil.disk_usage()` returns bytes; convert to GB with `/ (1024**3)` for readability in issue body.
- nvidia-smi uses `asyncio.create_subprocess_exec(['nvidia-smi', '--query-gpu=memory.total,memory.used,temperature.gpu,utilization.gpu', '--format=csv,noheader,nounits'])` and parses the CSV output.
- If nvidia-smi fails (no GPU, driver issue), log the error and set VRAM/GPU metrics to "N/A" rather than failing the whole report.
- Postgres database size: `async with pool.acquire() as conn: await conn.fetchval("SELECT pg_database_size('nova')")` returns bytes; convert to GB. Import `get_pool` from `app.db`.
- The trend issue body uses a markdown table format that is parseable (lines start with `|`). The previous data is embedded as a JSON comment at the bottom of the issue body: `<!-- trend-data: {json} -->`. This allows machine-parseable trend tracking across weeks. The JSON stores a list of weekly snapshots.
- Thresholds (module-level constants, tunable):
  - `DISK_WARN_PCT = 80`
  - `DISK_CRIT_PCT = 90`
  - `VRAM_WARN_PCT = 85`
  - `VRAM_CRIT_PCT = 95`
  - `GPU_TEMP_WARN = 80`
  - `DELTA_ALERT_PCT = 10`
- The trend data JSON structure in the HTML comment:
  ```json
  {"metrics": {"disk_pct": 65.2, "vram_pct": 42.1, ...}, "date": "2026-07-12"}
  ```
- Guard: if `settings.forgejo_token` is empty, log findings to console instead of filing.

The module exports `run_trend_report()` as the scheduler entry point.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Nova-core container → Docker socket | Host-level Unix socket — docker run/exec/stop/rm for scratch container |
| Nova-core container → Postgres (scratch) | Ephemeral scratch container on same Docker network |
| Nova-core container → Host filesystem | Mounted backup dump directory |
| Nova-core → nvidia-smi subprocess | GPU metrics via host NVIDIA driver |
| Nova-core → Forgejo API | Internet — issue creation with trend data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-11 | Elevation of Privilege | Docker socket — scratch container creation | critical | mitigate | Only specific docker commands (run, exec, stop, rm) with controlled args; no user-controlled container names or images; scratch container is short-lived (<5 min) and removed after use |
| T-29-12 | Information Disclosure | Backup dump in scratch container | medium | mitigate | Scratch container is removed within minutes of creation; no port exposure; same Docker network — no external access |
| T-29-13 | Tampering | Trend report JSON in issue body | low | accept | Stored as HTML comment in Forgejo issue body; parsed back by the agent; if tampered, next run treats as first run (no crash) |
| T-29-14 | Denial of Service | nvidia-smi subprocess hanging | medium | mitigate | All subprocess calls have 30s timeout; failure is graceful (metrics show "N/A", report still filed) |
| T-29-15 | Information Disclosure | System metrics (disk, VRAM) in Forgejo issue | low | accept | Private Forgejo instance; system utilization is operational data, no PII |
</threat_model>
