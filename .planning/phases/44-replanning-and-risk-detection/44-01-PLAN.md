    **1. Risk types and scoring**

    Define a helper type for risk results — use a plain dict with this shape:
    ```python
    # RiskResult is dict with keys:
    #   task_id: str
    #   title: str
    #   assignee: str
    #   score: float       # 0.0 (safe) to 1.0 (critical)
    #   level: str         # "low", "medium", "high", "critical"

    #   due_at: str | None
    ```

    `compute_risk_score(task: dict, blocks: list[PlannedBlock], calendar_events: list[dict]) -> dict`
    — Produce a per-task risk assessment. Called by `get_at_risk_tasks()` for every active task.

    Algorithm:
    1. **Base score** from `compute_score(task)` already gives 0-1 for priority + deadline proximity. Use it as the starting point.
    2. **Overdue penalty**: if `hard_deadline` is past `now`, add 0.25 (capped at 1.0).
    3. **Due-today proximity**: if `due_at` is today and remaining hours &lt; duration, add 0.15.
    4. **Capacity factor**: call `_estimate_day_capacity(task)` — if the user's day is &gt;80% full on days before the deadline, add 0.10.
    5. **Blocker factor**: if `blocked_by` dependencies exist and are incomplete, add 0.10.
    6. **Duration pressure**: if `task_duration_min &gt; 120` and deadline is within 48h, add 0.05.
    7. **Level mapping**: score &gt; 0.8 → "critical", &gt; 0.6 → "high", &gt; 0.3 → "medium", else "low".
    8. **Factors list**: append a human-readable string for each trigger that pushed the score above the base (e.g. "Overdue by 2 days", "Schedule is 85% full on deadline day").

    Clamp final score to [0.0, 1.0].

    - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -

    **2. Get at-risk tasks**

    `async get_at_risk_tasks(user: str, lookahead_days: int = 7) -> list[dict]`
    — Return all active tasks for `user` with risk scores, sorted by score descending (highest risk first).

    1. Fetch active tasks from DB (same query pattern as `planning._fetch_tasks`, but also fetch `assignee_name` via JOIN on users).
    2. Fetch existing planned blocks via `load_blocks(pool, user, today, today + lookahead_days)`.
    3. Fetch calendar events via `_fetch_calendar_events(today, today + lookahead_days)`.
    4. For each task, call `compute_risk_score(task, blocks, events)`.
    5. Sort by score descending. Return list of risk dicts.

    If user is "household", fetch all active tasks across all assignees. Use the existing household query pattern from `planning._fetch_tasks`.

    **3. Capacity check**

    `async compute_capacity_utilization(user: str, start_date: date, end_date: date) -> dict`
    — Return how full the planned schedule is per day and overall.

    Return shape:
    ```python
    {
      "per_day": [
        {"date": "2026-07-15", "planned_minutes": 420, "available_minutes": 840, "utilization": 0.5},
        ...
      ],
      "overall": {"planned_minutes": 840, "available_minutes": 1680, "utilization": 0.5},
      "peak_day": {"date": "2026-07-15", "utilization": 0.85},
    }
    ```
    1. Load planned blocks for the user in range.
    2. Load calendar events in range.
    3. Available minutes per day: working day length (WORK_DAY_END - WORK_DAY_START) in minutes, minus occupied event minutes.
    4. Planned minutes per day: sum of planned block durations.
    5. Return the dict.

    Use the same `WORK_DAY_START=8`, `WORK_DAY_END=22` constants from planning.py (import them).

    **4. Next-best-action computation**

    `async compute_next_best_action(user: str) -> dict`
    — Return the single most impactful actionable item for the user right now.

    Algorithm:
    1. Call `get_at_risk_tasks(user, lookahead_days=7)`.
    2. If no tasks, return `{"has_next_action": False, "message": "No tasks to recommend."}`.
    3. Walk the sorted risk list (highest risk first). For each task:
       a. Check if there is an available slot before the task's deadline.
       b. Use `find_available_slots` from planning.py for today + tomorrow (the next 2 days) to find a fitting slot for this task's duration.
       c. If a slot exists, this is the next best action.
    4. If no task has an available slot in the next 2 days, pick the highest-risk task regardless (it needs attention even if no slot is free — the household needs to make room).
    5. Return dict:
    ```python
    {
      "has_next_action": True,
      "task_id": "...",
      "title": "Prepare quarterly report",
      "assignee": "Ruben",
      "risk_level": "high",
      "recommended_slot": {"date": "2026-07-15", "start": "14:00", "end": "15:00"} | None,
      "reasoning": "Due tomorrow, high priority, your next free slot is today 14:00-15:00.",
    }
    ```

    - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -

    **5. Replan trigger**

    `async replan_if_needed(user: str, affected_date: date, reason: str, days_forward: int = 7) -> bool`
    — Check whether the current plan is still valid after a change; if not, trigger regeneration.

    1. Get DB pool.
    2. Load existing planned blocks for user in [affected_date, affected_date + days_forward].
    3. Fetch current calendar events for the same range.
    4. For each existing planned block that is NOT is_occupied, check whether it falls inside a now-occupied slot.
       A block is "conflicted" if a calendar event overlaps it.
    5. If any conflicted blocks found:
       - Log the conflict: `log.info("replan triggered for %s: %d blocks conflicted by %s", user, count, reason)`
       - Launch background `asyncio.create_task(generate_plan(user, affected_date, affected_date + days_forward, regenerate=True))`
       - Return True.
    6. If no conflicts, return False (no replan needed).

    Handle the case where `user` is "household" — in that case, check across all users (load their blocks separately, or use household blocks directly).

    Also provide an overloaded variant:

    `async replan_after_task_change(user: str, task_id: str, reason: str) -> bool`
    — Triggered when a task is added or completed. Check if the task falls within the existing plan window; if so, regenerate.

    1. Get DB pool.
    2. Fetch the task's due_at and planning_state.
    3. If due_at is within the next 7 days, or planning_state is "scheduled":
       - Launch `asyncio.create_task(generate_plan(user, today, today + 7, regenerate=True))`
       - Log: `log.info("replan triggered for %s: task %s changed (%s)", user, task_id, reason)`
       - Return True.
    4. Otherwise return False.

    ```python
    async def check_at_risk_tasks():
        """Check all users for at-risk tasks and send escalation messages.

        Replaces `check_overdue_tasks` with risk-aware escalation:
        - critical risk → immediate alert with specific warning
        - high risk → reminder with "due soon" message
        - medium risk → gentle heads-up
        """
        pool = await get_pool()
        async with pool.acquire() as conn:
            user_rows = await conn.fetch(
                "SELECT name FROM users WHERE name IN ('Ruben', 'Meral')"
            )

        for row in user_rows:
            user_name = row["name"]
            at_risk = await get_at_risk_tasks(user_name, lookahead_days=7)
            if not at_risk:
                continue

            # Critical: immediate alert
            critical = [t for t in at_risk if t["level"] == "critical"]
            for task in critical:
                factors = "; ".join(task["factors"])
                alert = (
                    f"⚠ Critical: '{task['title']}' is at risk of missing its deadline.\n"
                    f"Factors: {factors}"
                )
                await send_to_user(user_name, alert, proactive=True)

            # High: daily reminder level
            high = [t for t in at_risk if t["level"] == "high"]
            if high:
                titles = ", ".join(f"'{t['title']}'" for t in high[:3])
                alert = f"Reminder: {titles} {'and more ' if len(high) > 3 else ''}need attention soon."
                await send_to_user(user_name, alert, proactive=True)

            # Medium: summary in briefing only, not as separate alerts
            # (handled by the morning briefing integration below)
    ```

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-44-01 | Denial of Service | Task-update replan hook | low | mitigate | `replan_after_task_change` is fire-and-forget via `asyncio.create_task` — a failing replan does not block the tool response. Logs the error and continues. |
| T-44-02 | Denial of Service | Calendar-change replan hook | low | mitigate | Same fire-and-forget pattern as T-44-01. Conflicting events trigger at most one replan per event creation. |
| T-44-03 | Denial of Service | `check_at_risk_tasks` hourly job | low | mitigate | Job runs at most once per hour. `get_at_risk_tasks` is bounded by the active task count (typically &lt;50) and lookahead (7 days). |
| T-44-04 | Tampering | Replan override of manual blocks | low | accept | `generate_plan(regenerate=True)` deletes and rewrites all blocks in range. If a user manually placed a block, a triggered replan will overwrite it. Mitigation: the regenerate flag is only used by the replan trigger and the explicit `generate_plan` tool call — users know the tool regenerates. |
| T-44-05 | Info Disclosure | Dashboard SSE risk payload | low | accept | LAN-only trust (same as existing dashboard streams). Risk data is derived from tasks already visible in `/dashboard/tasks`. No new sensitive data exposure. |
