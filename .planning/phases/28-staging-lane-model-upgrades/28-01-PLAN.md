<action>
The production and staging compose stacks need to share a Docker network so nova-staging can reach the postgres and ollama containers without re-declaring them.

**Step 1 — Declare an external network**

Add a top-level `networks` block at the end of `docker-compose.yml`:

```yaml
networks:
  nova-net:
    name: nova-net
    external: false
```

This creates a bridge network named `nova-net` that both compose stacks can reference. Using `external: false` (default) means Docker Compose creates it when the production stack starts.

**Step 2 — Attach all existing services to the network**

For every service in `docker-compose.yml` (nova-core, postgres, ollama, whisper, piper, vector, ops-bridge, radicale, caddy), add:

```yaml
networks:
  - nova-net
```

Preserve each service's existing config (ports, volumes, depends_on, deploy, healthcheck, env_file, build, restart). The `networks` key is additive — existing `ports` and `volumes` are unchanged.

**Step 3 — Remove `ports` from services that don't need host exposure**

Only services that directly receive inbound traffic need `ports`:
- `nova-core`: port 8080 (kept)
- `ops-bridge`: port 8085 (kept)
- `whisper`: port 10300 (kept — Wyoming protocol)
- `piper`: port 10200 (kept — Wyoming protocol)
- `radicale`: port 5232 (kept — CalDAV)
- `caddy`: ports 80, 443 (kept — HTTP/S ingress)
- `postgres`: does NOT need a host port mapping in production (only accessed by other containers on the internal network). Remove its `ports:` block if present. If already absent (current file has no ports for postgres), leave as-is.
- `ollama`: does NOT need host port mapping in production (only accessed by nova-core containers on internal network). Remove `ports:` block if present. If already absent, leave as-is.
- `vector`: does NOT need host port mapping.

**Note on Coolify:** Coolify manages port exposure separately. Removing host port mappings from internal-only services is an improvement that prevents accidental host-level database access. Coolify's own reverse proxy (Traefik/Caddy) will handle external exposure for nova-core and ops-bridge.

**Per D-03:** Same GPU shared between staging and production — ollama is the single shared instance. No GPU changes needed.

Do NOT change any service's image, build, env_file, volumes, depends_on, healthcheck, deploy, or restart configuration. Only add `networks: - nova-net` and remove unnecessary `ports:`.
</action>

<action>
Create `docker-compose.staging.yml` — a standalone Compose file defining the `nova-staging` service that connects to the same postgres and ollama instances as production but uses a separate database and port.

Per D-01: `docker-compose.staging.yml` with `nova-staging` service.
Per D-02: Separate DB schema — different Postgres database `nova_staging`.
Per D-03: Same GPU shared — references production's ollama container.

```yaml
# Nova staging stack — deployed alongside production for model evaluation
# and change validation. Connects to the same Postgres and Ollama instances
# as production but uses a separate database (nova_staging) and port.
#
# Usage: docker compose -f docker-compose.staging.yml up -d
# (Requires the production stack to be running on the nova-net network.)

services:
  nova-staging:
    build: ./services/nova-core
    entrypoint: ["/app/staging-entrypoint.sh"]
    env_file: .env.staging
    depends_on:
      postgres:
        condition: service_healthy
        restart: true
      ollama:
        condition: service_started
        restart: true
    ports:
      - "8081:8080"
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')"]
      interval: 30s
      timeout: 5s
      retries: 3
    networks:
      - nova-net

networks:
  nova-net:
    name: nova-net
    external: true
```

Key design decisions:

1. **`entrypoint` override** — Uses `/app/staging-entrypoint.sh` instead of the default uvicorn command. This script creates the staging database if missing, runs migrations, then starts uvicorn. The script is built into the same Docker image (copied in the Dockerfile — see Task 3).

2. **`depends_on` with `restart: true`** — Ensures nova-staging waits for postgres (healthy) and ollama (started) before starting. The `restart: true` tells Docker Compose to restart the dependency container if it's not already running — but since production's postgres and ollama are already running, this is a safety net for ordering.

3. **Port 8081** — Maps host 8081 to container 8080, avoiding conflict with production's 8080.

4. **`external: true` on the network** — Tells Docker Compose that `nova-net` already exists (created by the production stack). The staging stack joins it.

5. **No GPU reservation** — Staging doesn't need its own GPU because it shares production's ollama (D-03).

6. **No duplicated services** — postgres, ollama, whisper, piper, vector, ops-bridge, radicale, caddy are NOT declared here. They are accessed via the shared nova-net network.

**Env vars** — The `.env.staging` file (Task 3) overrides:
- `POSTGRES_DB=nova_staging` — separate database, same postgres instance
- `NOVA_MODEL` — can differ from production for model comparison
- `NOVA_ENV=staging` — runtime environment indicator
- Port 8081 — handled by docker-compose.yml ports mapping

Ollama is accessed at `http://ollama:11434` (same DNS name as production) since both containers are on the same Docker network.

**Per D-02 (separate DB schema):** The database `nova_staging` does not yet exist in Postgres. It is created by the staging entrypoint script (Task 3) on first startup. Alembic migrations then create the full schema in that database.

### Step 3A — `services/nova-core/staging-entrypoint.sh`

A bash entrypoint that:
1. Creates the `nova_staging` database if it doesn't exist (connects to the `postgres` default DB first using POSTGRES_USER/POSTGRES_PASSWORD)
2. Runs Alembic migrations against `nova_staging`
3. Starts uvicorn

```bash
#!/usr/bin/env bash
# Staging entrypoint: create staging DB, run migrations, start uvicorn.
# Only runs in the nova-staging container (via docker-compose.staging.yml entrypoint override).
# Production uses the default Dockerfile CMD (uvicorn directly).

set -euo pipefail

# Extract connection parameters from environment (same vars as production, but POSTGRES_DB=nova_staging)
PGHOST="${POSTGRES_HOST:-postgres}"
PGPORT="${POSTGRES_PORT:-5432}"
PGUSER="${POSTGRES_USER:-nova}"
PGPASSWORD="${POSTGRES_PASSWORD}"
PGDB="${POSTGRES_DB:-nova_staging}"

echo "staging-entrypoint: ensuring database '$PGDB' exists on $PGHOST:$PGPORT ..."

# Create the database if it does not exist.
# We connect to the 'postgres' maintenance database to issue CREATE DATABASE.
PGPASSWORD="$PGPASSWORD" psql -h "$PGHOST" -p "$PGPORT" -U "$PGUSER" -d postgres -tc \
  "SELECT 1 FROM pg_database WHERE datname = '$PGDB'" | grep -q 1 \
  || PGPASSWORD="$PGPASSWORD" psql -h "$PGHOST" -p "$PGPORT" -U "$PGUSER" -d postgres -c \
       "CREATE DATABASE $PGDB OWNER $PGUSER"

echo "staging-entrypoint: database ready, running Alembic migrations ..."

# Run Alembic migrations against the staging database.
# (The database URL is built from env vars; ensure POSTGRES_DB=nova_staging is set in .env.staging)
cd /app
python -m alembic upgrade head

echo "staging-entrypoint: migrations complete, starting uvicorn ..."

# Start uvicorn on 0.0.0.0:8080 (as the Dockerfile CMD would, but done here explicitly)
exec uvicorn app.main:app --host 0.0.0.0 --port 8080
```

The script uses `psql` (PostgreSQL client) which must be available in the container. The `python:3.12-slim` base image does not include it by default. Add `postgresql-client` to the Dockerfile in Step 3B.

### Step 3B — Update `services/nova-core/Dockerfile`

Add `postgresql-client` install in the `base` stage so the staging entrypoint's `psql` command works. Also copy the staging entrypoint script.

Locate the `RUN pip install --no-cache-dir -r requirements.txt` line in the `FROM base AS base` section (line 9). Add after it:

```dockerfile
# psql client for staging-entrypoint.sh (database creation)
RUN apt-get update && apt-get install -y --no-install-recommends postgresql-client \
    && rm -rf /var/lib/apt/lists/*
```

Then locate the `COPY app ./app` line in the `FROM base` final stage (line 20). Add after it:

```dockerfile
COPY staging-entrypoint.sh .
RUN chmod +x staging-entrypoint.sh
```

This ensures the script is present in the final image at `/app/staging-entrypoint.sh` (the WORKDIR is `/app`).

The `tester` stage inherits from `base` and does NOT need the entrypoint — it only runs `pytest`. The `FROM base` final stage includes it for deployment.

### Step 3C — `.env.staging.example`

Create the staging env template. All values default to the same as production except where overridden.

```bash
# ─── Nova staging environment (copy to .env.staging) ───
# Overrides the production .env for the nova-staging service.
# Values not set here inherit from the Docker build context or default in config.py.

# Core — distinguish staging from production
NOVA_ENV=staging
NOVA_LOG_LEVEL=INFO
NOVA_TIMEZONE=Europe/Amsterdam

# LLM (Ollama) — shared with production; can override model for testing
OLLAMA_BASE_URL=http://ollama:11434
NOVA_MODEL=qwen3:14b           # ← Change this to test a different model on staging
NOVA_EMBED_MODEL=nomic-embed-text
NOVA_VISION_MODEL=llava

# Database — separate database on the same Postgres instance (D-02)
POSTGRES_HOST=postgres
POSTGRES_PORT=5432
POSTGRES_DB=nova_staging       # ← Different from production's "nova"
POSTGRES_USER=nova
POSTGRES_PASSWORD=${POSTGRES_PASSWORD}

# Tracing — enabled per default; Phase 26 traces provide benchmark data
NOVA_TRACING_ENABLED=true

# Staging-specific settings (optional overrides)
# NOVA_MODEL=my-experimental-model:latest   # Uncomment to test a different model
# NOVA_MAX_ITERATIONS=8                     # Staging can be more permissive
# NOVA_MAX_TURN_TIMEOUT=180                 # Longer timeout for eval workloads
```

**Important note on secrets:** The staging `.env` file needs the `POSTGRES_PASSWORD` from production. Since both staging and production share the same Postgres instance, `POSTGRES_PASSWORD` must match. In Coolify, this is managed via the Coolify UI — the `.env.staging` file on the server references the same secret.

**Per D-02:** Using `POSTGRES_DB=nova_staging` isolates the staging data in a separate database within the same Postgres instance. The entrypoint script creates this database if it doesn't exist.
**Per D-03:** Shared GPU via same `OLLAMA_BASE_URL=http://ollama:11434`.
**Per D-06:** Tracing is enabled by default in staging — traces from both staging and production go to the same OpenObserve instance, enabling before/after comparison.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| nova-staging → postgres | Staging service accesses the same Postgres instance with separate DB |
| nova-staging → ollama | Staging service shares GPU-accelerated LLM inference with production |
| nova-staging → nova-net | Network-accessible from other containers on the shared bridge |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-01 | Information Disclosure | staging DB in shared postgres | medium | mitigate | Separate database `nova_staging` with same auth credentials; isolation is at DB level, not user level. Staging uses production's auth — acceptable because both stacks run in the same trusted environment on the Nova VM. |
| T-28-02 | Denial of Service | shared ollama GPU contention | medium | mitigate | Staging and production share the same ollama process. Under concurrent load, both may experience latency. This is intentional per D-03 — the purpose is to validate new models under realistic contention. Monitor via Phase 26 tracing. |
| T-28-03 | Tampering | staging entrypoint creates database | low | mitigate | The entrypoint script connects to postgres with the same credentials as production and creates the staging database. This runs only once (if not exists) and is idempotent. The psql command is parameterized — no SQL injection from env vars (database name is fixed to `nova_staging`). |
| T-28-04 | Spoofing | staging service joins nova-net | low | accept | Both stacks run on the same trusted Nova AI VM. The shared network is intentional for service discovery. No unauthenticated external access to the bridge network. |
| T-28-SC | Supply Chain | postgresql-client package | low | accept | `postgresql-client` is an official Debian package from the Python 3.12-slim base image's apt sources. No new Python packages are added. |
</threat_model>
